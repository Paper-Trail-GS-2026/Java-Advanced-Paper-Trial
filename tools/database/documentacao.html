PT-DB-BASE-2 · 09/11/2026 · Base inicial para revisão e testes

Leitura rápida

Oracle: 10 tabelas, com catálogo Java e preparativos .NET separados por propriedade. Dataset fictício: 3 serviços, 8 requisitos, 7 preparativos e 14 itens. Um script autônomo, papertrail.sql, reúne modelo, carga e testes da base.

Apenas obrigatórios decidem progresso. Vazio e somente opcionais resultam em 0% e não ficam prontos. O modelo guarda snapshots pessoais e prevê auditoria e idempotência.

Problema e alcance

O PaperTrail ajuda o cidadão a consultar requisitos e organizar um checklist antes de procurar um serviço público. O checklist não garante atendimento, aprovação ou elegibilidade. O MVP prevê três serviços de uma cidade, ainda por selecionar. Não recebe documentos pessoais ou pagamentos.

Este PDF reúne o modelo inteiro e suas regras. A base possui DDL, dados e testes escritos. Packages, gatilhos, blocos demonstrativos, MongoDB e relatórios continuam pendentes; isso não constitui a entrega final da disciplina.

Ambiente inicial: Oracle da FIAP

Usar a conta acadêmica existente, com os objetos do PaperTrail separados por prefixo PT_. Endereço registrado no histórico do ClyvoCare: oracle.fiap.com.br:1521, serviço ORCL. Conexão e instalação da base confirmadas em 09/11/2026 no Oracle Database 19c Enterprise Edition. A conta acadêmica é a mesma do ClyvoCare; a criação ficou restrita aos nomes do PaperTrail.

Não há usuário ou senha neste documento ou no SQL. Não reutilizar entidades, migrations ou objetos do ClyvoCare. Na mesma conta podem existir tabelas de outros trabalhos; elas não devem ser removidas.

Executar o script único

  1. Conectar no SQL Developer, SQLcl ou SQL*Plus com a conta FIAP do próprio integrante.
  2. Conferir a conexão e abrir docs/database/papertrail.sql.
  3. No SQL Developer, executar como script (F5). No SQLcl/SQL*Plus: @docs/database/papertrail.sql, a partir da raiz do repositório.
  4. Guardar a saída real. A fase de testes deve terminar com a mensagem de sucesso. Uma mensagem de erro interrompe a execução.
Antes do DDL, o script consulta os nomes existentes e interrompe se encontrar objetos ou constraints reservados ao PaperTrail. Não contém DROP, TRUNCATE ou limpeza automática. Não reexecutar sobre uma instalação já existente.

Ordem: verificação de nomes → tabelas Java → tabelas .NET → dados fictícios → COMMIT da carga → testes com rollback das alterações de teste. Oracle confirma DDL implicitamente; uma falha posterior pode deixar objetos criados. Não executar com transação de trabalho pendente. Se houver erro, revisar os objetos identificados, sem apagar o schema ou objetos de outros projetos.

DDL usa Oracle 19c como referência de sintaxe. A versão 19c, as permissões e a quota necessárias à instalação desta base foram verificadas pela execução real na FIAP. Os testes escritos cobrem contagens, constraints, identity, unicidade de idempotência e rollback; não comprovam concorrência ou integração HTTP.

Arquivos e manutenção

A documentação Java à a origem do material. docs/database/ contém somente este PDF e o script papertrail.sql. Quando o .NET existir, copiar os mesmos artefatos, sem editar as cópias independentemente.

Os fontes de manutenção ficam em tools/database/: documentacao.html, fixtures.json e generate-fixtures.mjs. O HTML à o fonte editável deste PDF; para regenerar, abrir no navegador e imprimir em PDF A4, com gráficos de fundo e sem cabeçalhos automáticos.

node tools/database/generate-fixtures.mjs --check
node tools/database/generate-fixtures.mjs

O primeiro comando valida os dados e confere o trecho gerado dentro do SQL. O segundo regenera somente a seção de fixtures, preservando DDL, testes e comentários. Nenhum deles conecta a banco. Não há dependência npm adicional.

Contextos e relacionamentos

Setas contínuas são FKs. Pontilhadas representam contratos lógicos, não joins obrigatórios nem integrações implementadas. PT_IDEMPOTENCIA guarda o resultado da operação sem depender da existência posterior do preparativo.

O catálogo Java não consulta tabelas privadas do .NET. O .NET recebe dados do catálogo por HTTP e verifica identidade pelo JWT. Nos testes iniciais, os objetos PT_ usarão a mesma conta/schema FIAP do ClyvoCare, sem modificar os objetos existentes. Os contextos continuam separados por propriedade, sem FK entre eles.

Chave composta evita duplicidade por cidadão/operação/chave. Não há ID adicional nem FK para o preparativo; apagar o recurso não deve tornar uma chave antiga nova. O replay devolve o resultado original registrado.

A API deverá definir serialização canônica do payload, validar o limite da chave, comparar o hash, retornar 409 por conteúdo divergente e tratar corrida pela constraint. A gravação é feita junto ao preparativo/itens, com rollback do conjunto em falha. Este DDL não implementa o fluxo nem comprova concorrência. TTL/expurgo não foi incluído porque não foi definido no contrato.
